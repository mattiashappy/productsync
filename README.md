# ProductSync

A single dashboard to manage products and sync them across **WooCommerce** and **Shopify**.
A booking-platform adapter is planned for a later phase.

## Field-level sync rules

| Field | Direction | Conflict rule |
|---|---|---|
| `title`, `description`, `images`, `tags`, `categories` | dashboard → channels | dashboard wins |
| `price`, `compare_at_price` | dashboard → channels | dashboard wins |
| `inventory_quantity` | channels → dashboard | append-only orders, never overwritten by dashboard edits |
| `status` (active/archived) | dashboard → channels | dashboard wins |
| Order data | channels → dashboard | append-only |

Real paid orders are sacred — dashboard edits never overwrite them. Content/price flow outward; inventory and orders flow inward.

## Local development

```bash
cd productsync
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
# Generate ENCRYPTION_KEY:
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
# Paste it into .env

# Initialize database
flask db upgrade

# Start Redis in another terminal (required for the worker):
#   docker run -p 6379:6379 redis:7
# Or install Redis locally.

# Start the worker (separate terminal):
rq worker -u $REDIS_URL productsync-default

# Start the web server:
flask --app wsgi run --debug
```

Default seeded login: `admin@example.com` / `changeme123` (change immediately).

## Heroku deploy

ProductSync supports three environments — testing, staging, production — all driven from the same git repo via separate Heroku apps + remotes.

See [DEPLOY.md](DEPLOY.md) for the full walkthrough. Short version:

```bash
# One-time per stage:
./scripts/heroku-setup.sh test
./scripts/heroku-setup.sh staging
./scripts/heroku-setup.sh prod

# Daily deploys:
git push heroku-test main          # → testing
git push heroku-staging main       # → staging (after testing checks out)
git push heroku-prod main          # → production (after staging checks out)
```

The `release:` line in [Procfile](Procfile) runs `flask db upgrade` automatically on every push, so migrations apply before the new dynos take traffic.

## Architecture

See `../.claude/plans/so-i-would-like-ticklish-fountain.md` for the full design doc.

```
productsync/
├── wsgi.py                  # Heroku entrypoint
├── productsync/
│   ├── __init__.py          # Flask app factory
│   ├── config.py
│   ├── extensions.py        # db, login_manager, migrate
│   ├── models.py
│   ├── auth/                # login/logout
│   ├── catalogue/           # product CRUD UI
│   ├── addons_ui/           # addons catalogue + connect/manage stores
│   ├── orders_ui/           # read-only order log
│   ├── sync_ui/             # sync log + dashboard
│   ├── channels/            # adapters
│   │   ├── base.py
│   │   ├── woocommerce.py
│   │   └── shopify.py
│   ├── sync/                # sync engine
│   │   ├── rules.py
│   │   ├── push.py
│   │   ├── pull.py
│   │   └── reconcile.py
│   ├── webhooks/            # inbound webhook routes
│   │   └── routes.py
│   ├── jobs.py              # RQ task definitions
│   ├── scheduler.py         # APScheduler hourly reconcile
│   ├── crypto.py            # Fernet-based credential encryption
│   └── templates/
└── migrations/              # Alembic, generated by `flask db init`
```
